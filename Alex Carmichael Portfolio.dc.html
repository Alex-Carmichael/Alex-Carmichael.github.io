Scientific laboratory supplies — B2B ecommerce & CMS platform

A trade platform for laboratory supplies with a component-driven CMS behind it. Customers here don't shop like consumers: they buy against negotiated accounts, order for departments and outlets, and expect to see their own prices. I work across the Vue storefront, the .NET services behind it and the MySQL database underneath.

My work covers account dashboards, order history, favourites, account switching, account-specific pricing and the discount logic behind it, outlet and subsite pricing, sales and coordinator mappings, CMS component pages and navigation, and product search and indexing with Solr.

Screenshot — catalogue with account pricing

Fig. 1 — faceted Solr results with per-account price resolved inline.

Account pricing

Price isn't a property of a product here — it's the result of the customer's account, agreed discounts, contract lines and any outlet relationship. I moved that resolution into one place on the backend so the storefront, order history and CMS blocks all ask the same question and get the same answer, instead of each re-deriving pricing slightly differently.

Account switching

Buyers often act for several accounts. Switching has to swap pricing, permissions, order history and saved lists together, and never leave stale data from the previous account on screen. I made the active account part of the server-side request context and keyed client caches by it.

Product discovery

Search runs on Solr through SolrNet. I've worked on the index schema, filtering and facets, partial document updates for single-product changes rather than full reindexes, and the debugging search always needs — why a product ranks where it does, or why a filter excludes something it shouldn't.

CMS architecture

Content pages are assembled from reusable components rather than hand-built templates, including components embedded into subsites. Each component owns its data contract and rendering, so a new page is a composition rather than a development task.

Challenge

Pricing rules had accumulated over years and were being applied in several layers. Any change risked showing one customer another customer's price — the worst possible bug on a trade site.

Decision

Resolve prices server-side against the account context, keep the rules ordered and readable, and never cache a price without the account in the key. Slightly more work per request, far fewer ways to be wrong.

Result

Pricing behaviour is explainable — any displayed price can be traced back through account, discount and contract. New pricing requirements are configuration rather than another special case in the frontend.

What I learned

On business-critical logic, one authoritative implementation beats several convenient ones — and caching is where correctness quietly goes to die.

CMS page builder

Marketing pages used to arrive as development tickets: a layout, a developer building bespoke markup, a release. I built the tooling that turns that into an editorial job — pages assembled from reusable CMS components, configured rather than coded.

A complex page now goes together in about 20 minutes — with no developer involved.

Problem

Every campaign page needed developer time, so content moved at release speed.

Approach

A defined set of components with sensible defaults, rather than a free-form layout editor.

Result

Consistent pages, much less developer involvement, and layouts that can't be broken by accident.

The tension

Flexible builders become unusable; rigid ones send everyone back to the developers. I kept flexibility in composition — order, content, variant — and deliberately withheld it from styling and structure.

Implementation

Each component is a Vue component plus a typed configuration contract persisted against the page. Adding a type is one registration and one editor form; existing pages are untouched.

What I learned

Deciding what the tool won't let people do mattered more than any feature I added to it.

Most of the work was in SQL. Opportunity data was inconsistent after years of use, so the views had to normalise stages, handle missing values and aggregate without double-counting — CTEs kept each step's intent readable rather than producing one unreviewable query. The front end is Kendo UI inside the existing application, which meant fitting new widgets into conventions I didn't choose.

Hard part

Two people asking "what's in the pipeline?" meant different things. Before touching a query I had to get the definitions agreed — which stages count, whether value is weighted, what date a deal belongs to.

Trade-off

Kept aggregation in maintainable views rather than hand-tuned queries, then fixed the specific slow paths once real usage showed where they were.

What I learned

A dashboard is a data-modelling problem wearing a UI. The numbers only become useful once everyone agrees what they mean.

Request queue service

Two systems needed to exchange requests reliably without either being available at the same moment. I implemented queue processing for inbound and outbound requests: statuses, retries, failure handling and notifications when something needs a human.

System A — writes request
↓
Request queue — persisted, status: pending
↓
Processor — idempotency key, attempt count
retry — backoff
success — complete
failed — alert email
↓
External / internal system

Fig. 4 — every request has a persisted state; nothing leaves the queue without an outcome.

The requirement that shaped everything: a failed request must never silently disappear. Each one is persisted with a status and an attempt count before anything is sent, retried on a backoff, and escalated by email once it has clearly stopped being a transient problem. Because the receiving side wasn't always safe to call twice, retries carry an idempotency key so a retry can't duplicate work.

Failure modes I had to design for

Timeouts that actually succeeded, malformed payloads that would never succeed, and downstream outages where retrying is exactly right. They need different treatment — retry, park, or alert — so the status model had to distinguish them rather than lumping everything into "error".

Debuggability

Queue rows keep the payload, attempts and last error, so a production question can be answered by looking at the record instead of reproducing the incident.

What I learned

Reliability is mostly bookkeeping. The interesting engineering is in what you record before you make the call, not in the call itself.

How I work

Understand the problem, read the system that already exists, then make the smallest change that will hold up.

Start with the business problem

Requirements usually arrive as a symptom. I ask what someone is trying to do before deciding what to build, which regularly changes the answer.

Investigate before changing

In systems with years of history, the existing behaviour is the specification. I trace it through the code and the data before touching it.

Break features down

Large features get split into pieces that can be reviewed and released independently. Long-lived branches in shared systems cause their own problems.

Design for the next person

Maintainability over cleverness. If a rule is business-critical it belongs in one obvious place, not spread across three layers.

Work with legacy, not against it

Rewrites are rarely on the table. I improve things incrementally and keep new work consistent with what's already there.

Test the edges

Manual testing, Playwright and Selenium where it earns its keep, and deliberate thought about the odd cases — empty data, permissions, concurrent users.
